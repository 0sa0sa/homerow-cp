# キーボードナビゲーションアプリ 設計仕様書

## 背景・目的

macOS用のキーボード駆動UIナビゲーションアプリ「Homerow」(https://www.homerow.app/)を参考に、以下を満たす独自アプリをSwiftネイティブで開発し、オープンソースとして公開する。

- **速度**: ホットキー押下からラベル表示までの体感タイムラグをHomerowより短くする
- **デザイン**: ラベル・設定画面・モーションをRaycast水準の洗練度にする
- **配布**: GitHubで公開し、他者もビルド可能な構成にする

### Homerow調査サマリ

- macOSのAccessibility API (`AXUIElement`)でUI階層を走査し、クリック可能要素にキーボードラベルを表示、入力したラベルで即座にクリックできるツール
- 開発者(nchudleigh)の前身プロジェクト[Vimac](https://github.com/nchudleigh/vimac)はGPLv3でOSS化されており(Swift + AXSwift + RxSwift)、実装の参考になる。2022年に開発停止しHomerow(有料版)へ移行
- Vimacのissueでは、public Accessibility API (`AXUIElement`)がアクセシビリティサーバーとのIPC通信により遅いことが課題として挙がっている。これが「起動ラグ」の技術的根本原因と推測される

## スコープ(v1)

Homerow相当の基本機能 + 頻度ベースのラベル優先表示を実装する。カスタムコマンド/マクロ機能はv2以降とする。

- クリック可能要素の検出とキーボードラベル表示(左/右/ダブル/Commandクリック)
- テキスト検索によるラベル絞り込み
- スクロールモード(hjklでのスクロール領域ナビゲーション)
- キーバインドのカスタマイズ、マルチディスプレイ対応
- アプリ・要素ごとの使用頻度に基づくラベル優先割当

## 技術方針

**採用アプローチ**: 公開Accessibility APIを用いたバックグラウンド事前インデックス+キャッシュ方式(下記アーキテクチャ参照)を基本とし、非公開API (HIServices) を用いたさらなる高速化は将来のオプション機能として温存する(v1では実装しない)。

非公開APIを直接叩く方式は理論上さらに高速化できる可能性があるが、Appleの非公開実装に依存するためmacOSアップデートで破損するリスクが高く、OSSとして他者が保守する上でも脆いため、v1では採用しない。

## アーキテクチャ

主要コンポーネントを疎結合に分離する。

- **AccessibilityIndexer**(バックグラウンド常駐): `AXObserver`でフォーカスアプリ/ウィンドウの変化・レイアウト変更通知を購読し、クリック可能要素のツリーを非同期にスキャンして`WindowCache`に保持し続ける。ユーザー操作を待たずに裏で更新する。
- **HotkeyManager**: グローバルホットキーを監視し、押下されたら`OverlayController`を起動する。
- **OverlayController**: `WindowCache`から該当ウィンドウの要素一覧を即座に取得し、`LabelAssignmentEngine`でヒント文字列を割り当てて、透過`NSPanel`にSwiftUIでオーバーレイ描画する。
- **LabelAssignmentEngine**: 要素座標の重なり回避、ホームロー文字(`asdfghjkl`等)によるラベル生成、`FrequencyTracker`のスコアを使った優先順位付けを担当する。
- **SearchFilter**: オーバーレイ表示中の文字入力をリアルタイムに要素タイトル/roleへファジーマッチさせ、候補を絞り込む。
- **ActionExecutor**: 選択された要素に対し`AXUIElementPerformAction`や`CGEvent`合成でクリック系操作を実行する。
- **FrequencyTracker**: アプリ・要素単位の選択回数をローカルに記録し、`LabelAssignmentEngine`に供給する。
- **ScrollController**: スクロールモード(hjklでスクロール領域を移動)を担当する。
- **PreferencesUI**: SwiftUIによる設定画面。Raycastライクなデザイン言語で統一する。

`AccessibilityIndexer`と`OverlayController`を分離することで、「スキャン」と「表示」が独立し、キャッシュがあればオーバーレイは表示処理のみで済み、体感速度がAXツリー走査に律速されなくなる。

## データフロー

### バックグラウンド更新(ユーザー操作と非同期)

1. フォアグラウンドアプリ/ウィンドウが変わる(`NSWorkspace`の`didActivateApplicationNotification`) → 該当ウィンドウの`AXObserver`を張り替える
2. `AXObserver`が以下の通知を購読する: `kAXFocusedWindowChangedNotification`、`kAXUIElementDestroyedNotification`、`kAXLayoutChangedNotification`、`kAXWindowResizedNotification` など
3. 通知を受けたら、そのウィンドウのアクセシビリティツリーをバックグラウンドスレッドで再スキャンし、`WindowCache`(ウィンドウID→クリック可能要素リスト+座標)を更新する
4. スキャンは差分更新を基本とし、変化のなかった部分は再利用してコストを抑える

### ホットキー押下時(ユーザーが待つ経路)

1. `HotkeyManager`がトリガーする
2. `OverlayController`が現在のフォーカスウィンドウIDで`WindowCache`を即座に参照する
   - キャッシュがあれば、それを使って直ちにラベル描画する(ゼロレイテンシ化の核)
   - キャッシュがない/古い場合(初回起動直後など)のみ、その場で同期スキャンにフォールバックする(通常のHomerow相当の速度)
3. 表示中も裏では最新化が走り続け、次回以降のためのキャッシュ鮮度を保つ

### 要素選択後

1. `ActionExecutor`がクリック等を実行する
2. `FrequencyTracker`が対象要素の選択回数をインクリメントする(アプリ名+要素の安定した識別子をキーにする)
3. オーバーレイを閉じ、キャッシュはそのまま常駐継続する

## 頻度ベースのラベル優先表示

### 識別子の安定化

`AXUIElement`自体はプロセス再起動やUI再構築で不安定なため、`(バンドルID, windowロール, 要素role, 要素title/identifier, 画面内の相対位置)`から安定ハッシュを作り、これを`FrequencyTracker`のキーにする。完全一致しない場合はroleとtitleの近似一致でスコアを引き継ぐ。タイトルが動的に変わる要素は頻度追跡の対象外にフォールバックする。

### スコアリング

- アプリ単位・要素単位で選択回数を記録する(直近使用ほど重み付けが高い減衰つきカウント。例: 使うたびに+1、日次で減衰)
- 起動時にその時点で表示される要素群を頻度降順にソートする

### ラベル割当への反映

- ホームロー(`asdfghjkl`など)の中でも押しやすい/短いラベル(1文字)を頻度上位の要素に優先的に割当て、頻度が低い要素は2文字ラベルに回す
- 同一画面に同じ要素セットが繰り返し出る場合、ラベルの割当が毎回大きく変わると「体で覚えたショートカット」が崩れるため、同一セッション内・同一ウィンドウでは可能な限り前回と同じラベルを維持し、新規/変動要素にのみ新しいラベルを割り振る安定化ロジックを入れる

### 保存先

頻度データはローカルファイル(SQLite想定)に保存し、設定画面から「学習データをリセット」できるようにする。

## UI/デザイン(Raycastライクな見た目)

### ヒントラベル

- 角丸(6〜8px程度)の小さなカプセル型バッジ、半透明+背景ブラー(`NSVisualEffectView`ベース、ライト/ダークモード自動追従)
- タイポグラフィはSF Mono/SF Proの太字小サイズで視認性重視。頻度が高い要素ほどわずかに強調色をつける(オプション)
- 検索モードで文字を打つと、マッチしたラベルの一致部分をハイライトし、非マッチ候補はフェードアウトして視線誘導する
- 表示は「フェード+わずかな拡大」のスプリングアニメーション(0.1〜0.15秒程度)で、Raycastのポップ感を再現する。キャッシュ命中時はこのアニメーションのみがレイテンシとして体感されるようにする

### 設定画面(Preferences)

- SwiftUIのサイドバー+詳細ペイン構成(General / Keybindings / Appearance / Frequency Data / About)
- アクセントカラー1色+ニュートラルなグレースケール背景、コンパクトな行間のリスト表示
- キーバインド変更はレコーダーUI(クリックして押したキーを即反映)

### 操作時のフィードバック

- 要素選択時に対象要素へごく短いハイライト矩形フラッシュ
- モード切替(検索⇔スクロール)時にオーバーレイ全体がクロスフェードする

### 配色・ブランディング

アプリ独自のアクセントカラーを1つ決め、ライト/ダーク両対応のデザイントークンとして定義する。具体的な配色は実装フェーズでモックアップ確認のうえ決定する。

## エラーハンドリング / エッジケース

- **アクセシビリティ権限未許可**: 起動時にAPI呼び出し失敗を検知し、システム設定の該当ペインを開くよう促すオンボーディング画面を表示する。権限が付与されるまで機能を無効化する。
- **AXツリー走査がタイムアウトする重いアプリ**: 一定時間(例: 200ms)でスキャンを打ち切り、取得済みの部分だけでラベル表示する。取得漏れは以後のバックグラウンド更新で補完する。
- **非対応/AX非公開のアプリ**: 要素が0件だった場合はその旨を控えめに表示し、クラッシュさせずに終了する。
- **AXUIElementの無効化**: `AXUIElementPerformAction`が失敗した場合は静かに無視してオーバーレイを閉じるのみとする(エラーダイアログは出さない)。
- **マルチディスプレイ**: フォーカスウィンドウが乗っている画面のみにオーバーレイを表示する。
- **キャッシュの陳腐化**: バックグラウンド監視が取りこぼした変化に備え、オーバーレイ表示中に見えている座標と実際のスクリーン内容がズレていないか軽量チェックし、疑わしい場合のみ同期再スキャンにフォールバックする。

## テスト方針

- **ユニットテスト**: `LabelAssignmentEngine`(ラベル割当・安定化ロジック)、`FrequencyTracker`(スコア計算・減衰)、`SearchFilter`(ファジーマッチ)は純粋ロジックとして切り出し、XCTestで検証する。
- **AX連携部分**: 実際の`AXUIElement`はモック困難なため、テスト用の簡易ターゲットアプリ(Finder等)を使った手動/半自動の統合確認を中心にする。
- **パフォーマンス計測**: ホットキー押下からラベル描画までのレイテンシを計測するデバッグ用オーバーレイ(ms表示)を用意し、主要アプリ(Finder, Safari, VS Code, Slack)でキャッシュあり/なしの体感速度を数値で比較する。

## 配布方針

GitHubにてオープンソースとして公開する(ライセンスは実装開始時に別途決定)。App Store配布は前提としない(Accessibility APIの利用がサンドボックス制約と相性が悪いため、直接配布+notarizationを想定)。

## v2以降の検討事項(スコープ外)

- カスタムコマンド/マクロ登録(特定の操作シーケンスを1ショートカットで実行)
- 非公開API (HIServices) を用いた実験的高速化モード
